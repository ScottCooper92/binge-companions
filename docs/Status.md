# Status

This page shows where each contract and each platform piece stands. The stages are:

**Not started → In design → Draft → Spike-validated → Stable (published)**

- *Draft*: the `.proto` is in `contracts/`.
- *Spike-validated*: a real companion app has served the contract on hardware.
- *Stable*: the artifacts are on Maven Central. The append-only guarantee applies.

A contract can also be *Deferred*: a decision, not a stage in the progression above — set aside on
purpose, with what would bring it back written down.

_Last updated: 2026-11-09._

## Contracts

| Contract | Action | Stage | Notes |
| --- | --- | --- | --- |
| REQUEST | `com.binge.companion.REQUEST` | **Draft** | The v1 messages and `RequestService` are in `contracts/`. The transport spike held on a phone and a SHIELD-class TV (tracked privately), and the reference companion serves every v1 operation against a real Seerr instance (`ListRequests` and `GetStatuses` since ScottCooper92/binge-seerr#717). `REQUEST_FILTER_MINE_RECENTLY_AVAILABLE` and its capability, `CAPABILITY_LIST_MINE_RECENTLY_AVAILABLE`, are additive in the same `v1` package: the signed-in user's own recently available requests, which a host notifies from, since `RECENTLY_AVAILABLE` holds every user's (#193). Notification forwarding began here as `CAPABILITY_FORWARD_NOTIFICATIONS` and moved to the NOTIFICATIONS contract (below); that capability number and name are reserved. Request ids are opaque strings, so a provider with UUID or slug ids can serve v1; empty means unset (#119). That was a type change, accepted because v1 is still Draft. The same holds for the generic-provider revision: `is_4k` became a string `version_id` declared through `HandshakeResponse.versions` (which replaces `CAPABILITY_REQUEST_4K`; a companion that lists none has the standard version only), `ReportIssue` gained a version, a season, an episode and provider-defined categories (`CAPABILITY_ISSUE_CATEGORIES`, `ListIssueCategories`), `DeclineRequest` gained an optional `reason`, and `CancelRequest` is documented as never deleting media files. `buf breaking` fails on that revision by design, and the old numbers and names are reserved. `RequestInfo.quality_label` is additive in the same `v1` package: the destination quality profile's name for display, empty when the provider doesn't say. The stage moves once that companion has served the contract on hardware with production traffic. `CAPABILITY_SERVER_UNREACHABLE` is additive in the same `v1` package and declared the same way in REQUEST, LIBRARY and STREAM: the companion marks a call that failed because the server behind it did not answer, as a `SERVER_UNREACHABLE` `ErrorInfo` on `UNAVAILABLE` or `DEADLINE_EXCEEDED`, so a host can say it apart from a transport failure (#299). `CAPABILITY_DELETE_FILES` and the `DeleteFiles` rpc are additive in the same `v1` package: delete a title's downloaded files for one version, then withdraw its requests (#284). `VersionStatus.allowed_actions` (field 8) is new with it: the per-version capabilities, where the title-level list cannot say which version. |
| LIBRARY | `com.binge.companion.LIBRARY` | **Draft** | The user's own media server: availability, a play hand-off, watch state both ways, continue watching. The decisions are recorded in `Architecture.md`. Play is a hand-off Activity on `com.binge.companion.PLAY`, not an rpc: `GetPlayTarget`, `PlayTarget`, `AndroidIntent`, `IntentExtra` and `WebUrl` were removed, and `CAPABILITY_PLAY` now means the Activity exists (#117). That was accepted because nothing called the rpc. The v1 messages are in `contracts/` (#19); the SDK support is #20. Jellyfin is the first companion. `PLAYBACK_SOURCE` and `PLAYBACK_PROGRESS` landed additively: a source Binge's own player renders, with the device profile, subtitle files, chapters and skippable segments beside it, and live progress reported back against the session it came with. `Availability.reason` landed additively in the same `v1` package, with no capability (#303): `AVAILABILITY_REASON_SERVER_LACKS_IDS` on a `NOT_IN_LIBRARY` answer says the server holds titles with no id the integration can match on, so this one may be among them; `UNSPECIFIED` means no reason. An optional `Trickplay` on `GetPlaybackSourceResponse` (field 9) lets a companion hand Binge's own player seek-bar thumbnails, additively and with no capability (#291). `CAPABILITY_SERVER_UNREACHABLE` is declared here too, with the same meaning (#299). `WatchState.episodes` is now a window of the 100 most recently played, and empty in a `LibraryEntry`; `ListEpisodeWatchState` pages the full per-episode state behind `CAPABILITY_EPISODE_WATCH_STATE`. The two caps change what a conformant companion may send, with nothing on the wire changed (#287). The cleartext rule for playback sources is tightened, with nothing on the wire changed: `100.64/10` counts as private only while a VPN or overlay network is up, `::ffff:a.b.c.d` is classified by its IPv4 address, and the header states that the check bounds what the host accepts and not what an installed third-party player later fetches (#267). A source a companion served in cleartext to a `100.64/10` address with no overlay up is now dropped by the host. `PlaybackDeviceProfile.codec_limits` (field 8) is additive and carries no capability: the largest frame per video codec and profile, with the single `max_width` and `max_height` kept as the fallback (#315). |
| STREAM | `com.binge.companion.STREAM` | **Draft** | Playable sources that are not the user's library, as a server-streaming `Resolve` of shared `PlaybackSource`s. The v1 messages are in `contracts/`, and the host protections are recorded in `Architecture.md` > STREAM. Hand-off, and the host's own player beside it, behind a flag. Gated: no host ships STREAM UI until a first-party companion exists that resolves licit sources, and the stage moves once one has served it. Not deferred: binge-archive, that companion, is being built (#141), and so is Binge's STREAM host, behind a feature flag. `Resolve` answers sources, OK and empty, `NOT_FOUND` (not in the catalogue, not a failure) or `INVALID_ARGUMENT`. The host's `Resolve` deadline is 10 s (#148). A source carries its licence as `licence_label` and `licence_kind` (#247), and the file it plays as `file_name` (#265). `PLAYBACK_PROGRESS` landed additively: the companion keeps watch progress for its own sources, from `ReportPlayback`, and serves it back as `Resolve`'s resume point, a paged `ListContinueWatching` (a finished episode stays, as next up) and `ForgetProgress`. Binge keeps none. `ReportSource` and `CAPABILITY_REPORT_SOURCE` are deprecated: no host calls them and the one companion that declared it has dropped it. Nothing is removed or renumbered. `CAPABILITY_SERVER_UNREACHABLE` is declared here too, with the same meaning (#299). `CAPABILITY_LIST_SERVED_TITLES` and `ListServedTitles` are additive in the same `v1` package: a paged list of the TMDB ids the companion serves, filtered by the host's region and rating limit, which the host renders from TMDB (#149). It is a named exception in `Architecture.md` > Where STREAM stops. |
| NOTIFICATIONS | `com.binge.companion.NOTIFICATIONS` | **Draft** | The companion hands the host the notifications it would have shown itself: `SetNotificationForwarding`, `ListNotifications` (paged, polled on the host's schedule) and `AcknowledgeNotifications`, carried as the shared `ForwardedNotification` (`Architecture.md` > Notifications). Its own contract so a companion has one switch, one queue and one id space. A core `Handshake` with an empty capability set, so a later optional rpc can be gated by a capability. Needs no provider session. Moved out of REQUEST while both were Draft. |
| TRACKING | `com.binge.companion.TRACKING` | Not started | |
| PLAYER | `com.binge.companion.PLAYER` | Deferred | Binge's own player covers a LIBRARY title, and the Play sheet the players people already have (#51). See `Architecture.md` > Where LIBRARY stops and `Ecosystem.md` > Players for what would bring it back. |

## Platform pieces

| Piece | Stage | Notes |
| --- | --- | --- |
| `binge-companion-contracts` | Draft | Builds in this repository (protobuf-javalite + grpc-kotlin stubs). Consumed as source: Binge vendors a pinned copy of the `.proto` files, and binge-seerr includes this build through a submodule. Not yet published. |
| `binge-companion-sdk` | Draft | `sdk/` builds here: `IntegrationService` (Binder server bootstrap), `HostPolicy` (the Service's caller verification) and `HandOffPolicy` (the hand-off Activities': the advanced picker's, the view-request one's, the settings one's and the play one's, plus the host's `isStartable` check), `CompanionManifest` keys, hand-off actions and extras, the host title and companion links (`hostTitleUri`, `binge://title/…`; `hostCompanionUri`, `binge://companions/…`), Binge's Play listing URL, handshake helper. binge-seerr consumes it as source through the same submodule. `BingeHosts.release` pins release Binge's Play App Signing certificate, the one every Play install carries. Not yet published. |
| Conformance harness | Not started | Runs over any channel, so companion authors need no emulator. |
| Reference companion (Binge Seerr) | Draft | [binge-seerr](https://github.com/ScottCooper92/binge-seerr) serves every REQUEST v1 operation against the connected Seerr instance, the capability set is derived from the signed-in user's permissions, and the setup screen is built on the shared design system. The in-tree Seerr integration it replaces is deleted from Binge. |
| LIBRARY companion (binge-jellyfin) | Draft | [binge-jellyfin](https://github.com/ScottCooper92/binge-jellyfin) serves every LIBRARY v1 rpc against the signed-in Jellyfin user, with `PLAYBACK_SOURCE` and `PLAYBACK_PROGRESS`, and has played and resumed in Binge's player on a phone. Its own UI is sign-in (Quick Connect first, on phone and TV) and a console for the server, being built. Its device lane binds the Service over Binder on the minified build. |
| Host support in Binge | Draft | Binge hosts REQUEST, LIBRARY and STREAM. Discovery, consent and the grpc-binder client are written and unit-tested, and each REQUEST companion is exposed through a `RequestCompanion` contributed by the bridge. The bridge also has a LIBRARY host and a STREAM host. LIBRARY playback is behind `FeatureFlag.LIBRARY_PLAYBACK`; STREAM sources and playback are behind `STREAM_SOURCES` and `STREAM_PLAYBACK`, and the progress report back to a STREAM companion behind `STREAM_PROGRESS`. Binge's emulator lane drives bind → handshake → request between Binge and a stub companion over a real Binder, and the hardware spike measured latency, memory and APK cost (tracked privately). |
